## Design and decisions

### Locked account/role update (2026-09-20)

There is one account identity, not permanent DM/player account types. Campaign ownership, campaign role, session authority, character assignment and presentation mode are separate. The new character RPCs authorize an approved session participant regardless of anonymous/registered identity; owning another campaign gives no authority here. Management continues to use the existing campaign-owner permission helper. Anonymous identities never receive management authority. Authorized DMs, current-session DM handoff and owner seat recovery remain future work; this issue adds no role/view-mode bypass. Existing issue #6 enrollment screens remain guest-oriented, while the player lobby accepts either authenticated identity after server approval.

Approved session guests submit one assigned campaign character for separate DM character approval. A pending character is visible to its assigned guest and the DM; approved public party fields retain the existing RLS projection. Guest editing uses narrow typed RPCs for only their current assignment; private character details stay DM-only. The character form includes name, player name, HP/max/temp HP, AC, speed, statuses and explicitly shared notes. Creation/update timestamps and a canonical portrait path persist with the character.

DM hosts manage campaign characters from the session panel, approve them, intentionally issue/copy/regenerate/revoke a reclaim code, or recover them by assigning an approved guest. Reclaim uses the existing 256-bit hashed 30-day bearer-code model and prior session approval. Valid reclaim transfers control and clears previous assignments, preserving the established issue #5 contract. DM recovery revokes the previous code so a displaced holder cannot reclaim again. Plaintext codes live only in the current intentional issue panel; never browser storage or normal projections.

Portraits use the existing private bucket and an additional stable `campaign/character/portrait.png` path (legacy four-part paths remain unchanged). PNG/JPEG/WebP, maximum 5 MiB. The currently assigned guest can insert once, including before character approval; only the DM may replace/delete, matching the approved one-time-image spec. Authenticated download to an object URL supplies the preview; image data and object URLs are discarded on navigation/access loss. No external image hosting.

Contract (exact frontend interface):

- `create_session_character(p_session uuid,p_name text,p_player_name text,p_hp integer,p_max_hp integer,p_temp_hp integer,p_ac integer,p_speed integer,p_statuses text[],p_notes text) returns uuid`: approved session participant, anonymous or registered; campaign inferred server-side; no supplied owner. Creates an unapproved character and assigns it atomically only when the caller has no character assignment in that campaign. Field bounds: names 1–80 trimmed; HP -999..9999; max/temp HP 0..9999; AC 0..99; speed 0..999; <=20 statuses of 1–60 chars; notes <=2000. No strict game rules.
- `update_session_character(p_session uuid,p_character uuid, same field arguments as create) returns void`: current assigned approved-session guest or owning DM with matching session/campaign. Cannot change approval, campaign, assignment, image path or DM notes. Updates timestamp.
- `review_character(p_character uuid,p_approved boolean) returns void`: owner DM only; false revokes its reclaim code. Pending assigned guest may still read/edit submission but cannot reclaim it.
- `assign_character(p_session uuid,p_character uuid,p_user uuid) returns void`: owner DM; approved character, approved target membership/session, open session, matching campaign. Clears prior assignments across campaign; replaces target's old assignment; revokes character's prior code atomically. Other clients cannot call it. Log safe events.
- Existing `issue_character_code`, `revoke_character_code`, `reclaim_character` retain signatures and old assertions. Strengthen locking/revocation races as needed. A caller already controlling a DIFFERENT character must fail reclaim rather than orphaning a pending character; DM reassignment is the explicit override. Repeated reclaim of same character remains supported. Owning DM authority on issue/revoke; no code enumeration. Transfer with valid secret remains allowed as the established contract, not a presence-based lockout.
- `get_character_panel(p_session uuid) returns jsonb`: authorized DM or approved session guest only (others permission denied). `{characters: [...], players: [...], own_character_id: uuid|null}`. DM characters = all campaign characters. Guest characters = only own current assigned character, even pending; players empty. Character projection fields exactly id,campaign_id,name,player_name,approved,hp,max_hp,temp_hp,ac,speed,statuses,public_notes,image_path,created_at,updated_at,assignments. `assignments` array contains effective approved open-session rows with user_id,session_id,display_name (DM sees all; guest own only). DM `players` lists approved current-session guests as user_id/display_name for recovery dropdown. No private details/codes.
- `set_character_image(p_session uuid,p_character uuid) returns void`: only current assigned guest with effective session access, or owner DM/matching campaign. Validates that canonical bucket/path object exists; sets canonical image_path (no arbitrary path argument) and updates timestamp. Guest cannot reset an existing image path; DM may refresh after replacement.
